# HONESTY.md — what MIZAN-KSA is, and what it is not

This file states the boundaries of every claim. It is updated as each phase lands and finalized in Phase 11.

**How to read it.** It used to be one long list, which made a deliberate decision look the same as an unfinished
chore. It is now sorted into three, because they are not the same kind of thing and a reader should not have to
work that out:

- **[A -- what this project deliberately does not do](#a----what-this-project-deliberately-does-not-do).** Scope
  decisions, each with a reason.
- **[B -- what testing and review uncovered](#b----what-testing-and-review-uncovered).** Findings. Several are
  defects in other people's software, including ZATCA's own validator.
- **[C -- open, with the fix named](#c----open-with-the-fix-named).** Genuinely unfinished. Kept short.

## The short version (spec v1.1 Section 11)

- **Synthetic data.** All records come from a deterministic, fixed-seed generator (~100K rows). No real
  customer, merchant or tax data is used. The 20M-row figure is a local Docker Spark stress benchmark, not a
  Fabric production workload.
- **Not a certified tax product.** MIZAN-KSA implements ZATCA Phase-2 hashing and state rules as a
  standards-informed reference architecture. It is not ZATCA-certified and does not talk to the real Fatoora
  portal; a mock Fatoora server is used.
- **Signing.** ECDSA secp256k1 with a self-generated **test key**. Full XAdES signed-properties structure and
  ZATCA SDK certification are **out of scope** (ADR-006).
- **ERP.** GL lines are ACDOCA-*shaped*. No SAP system or binary cluster (RFBLG/BSEG) extraction is involved.
- **Privacy residual window.** Erasure is immediate for every analytical copy. The only residual window is
  OneLake's platform soft-delete, which MIZAN cannot shorten.
- **Regulatory interpretation.** PDPL/NDMO controls are configurable technical controls, not legal advice.
  Velocity rules are named as velocity rules; no SAMA clause is claimed.

Scope decisions, each made on purpose and each with a reason. Nothing here is unfinished: these are the
edges of the build, drawn where a real system would need a licence, a tenant, a vendor or a regulator that
a portfolio cannot have.

## B -- What testing and review uncovered

Findings, not limitations. Each of these was discovered by running something -- ZATCA's own validator, a
fault-injection harness, a scoring run against ground truth, or an external review -- and several are
defects in other people's software rather than this one's. They are listed here because a reader should be
able to tell a discovery from a chore, which the single flat list this file used to be made impossible.

| 2 | **Validated against ZATCA's own offline SDK** (Compliance Enablement Toolbox 3.0.8, LGPL v3). Our signed invoices pass its **XSD**, **EN 16931** and **KSA business-rule** stages. The SDK is not committed (39 MB, downloaded by hand behind ZATCA's terms checkbox); `scripts/validate_with_zatca_sdk.py` runs it and `tests/test_zatca_sdk_validation.py` skips cleanly when it is absent. | 2 | `BR-KSA-50` (line VAT = net x rate/100) fails on some lines **because the rule itself uses floating point**: the schematron compares with `=` and no tolerance, so for a line of 96.00 it computes `14.399999999999999` and rejects our exact `14.40`. MIZAN's money is `Decimal` throughout, which is why our value is right and the check drifts. Item prices are all multiples of 0.20 SAR so that 15% VAT lands exactly on the halala; the residual failures are the validator's binary-representation artefacts, not ours. `tests/test_zatca_sdk_validation.py` allows this one code and fails on any other KSA rule. | Stated |
| 2 | The SDK (3.0.8) reads QR **tags 8 and 9 as the signature's R and S**, while ZATCA's published spec defines them as the public key and the certificate's signature. We follow the published spec, so that part of the QR stage reports a mismatch. Tag 8 ships as the bare EC point and tag 9 as fixed-width r&#124;&#124;s: both are the spec's values, and the compact form is what keeps the QR inside the 500-character cap (`BR-CL-KSA-14`). | Stated |
| 2 | **The SDK's 4th stage, the QR cryptographic check, does not pass, and cannot.** Its rules contradict each other: `BR-KSA-68` makes `cbc:TaxCurrencyCode` mandatory, `BR-KSA-EN16931-09` then makes a second `cac:TaxTotal` mandatory, and the QR validator sums both TaxTotals (18.00 + 18.00) before comparing them to QR tag 5. No invoice can satisfy all three unless the QR states double the real VAT, which would be false. | 19 | **The reconciliation cannot see offsetting same-day errors, and this is now measured rather than assumed.** Five reviewers made the same point: the same author wrote the generator and the reconciler, so they share the rounding and fee rules and SAR 0.00 holds partly *by construction*. `tests/test_recon_fault_injection.py` answers it by damaging clean data on purpose -- 50 perturbations across six classes (halala drift on a capture, drift on a fee, a dropped settlement line, a duplicated one, an orphan bank line, GL posting drift), each on a fresh copy. **Detection recall is 1.000 for all six single-sided classes.** It was **0 for offsetting pairs**: +5.00 SAR on one capture and -5.00 on another, same merchant, same day, net to zero inside the `GROUP BY` and the day still reads SAR 0.00. **Closed on 2026-11-21 by the leg the row itself named.** `dbt/tests/assert_every_settled_line_matches_its_payment.sql` joins `payment_event_id` to its settlement line and fails on any non-quarantined row where the amount the bank settled differs from the amount the till captured -- line by line, with nothing summed, so two errors cannot hide behind each other. Recall for offsetting pairs is now **1.000**. **The merchant-day half has not changed and cannot:** no sum over a day can see two errors that cancel inside it, and the test now asserts *both* halves rather than only the flattering one. Quarantined lines are excluded because a mismatch is precisely why they are quarantined, and re-reporting it would turn a working control into a permanently red test. It is also a genuinely **independent** check rather than a restatement: Silver decides `settlement_status` by comparing these same two amounts at build time, and this runs at Gold build time against whatever the tables now hold, so a payment amount changed after Silver was built keeps its PAID_BANK status and this is the thing that notices. | Fixed |
| 20 | **The MDM ladder is scored, not described.** It was previously defended by one hard negative (the brothers) and one positive (five spellings of one customer) -- neither of which is a measurement, since a matcher that merged nothing passes the first and a matcher that merged everything passes the second. `tests/test_mdm_precision_recall.py` scores it pairwise against the generator's own `_person` ground truth over **3,967 records and 1,492 true pairs: precision 1.0000 (0 false merges), recall 0.9625, F1 0.9809**. Precision is asserted at exactly 1.000 and recall is recorded rather than demanded, because the two errors are not symmetric: a false merge joins two citizens into one identity (a PDPL incident and a corrupted audit trail), while a missed merge is a steward's queue item. The 56 missed pairs are overwhelmingly the cross-script ID-less records the ladder deliberately refuses to guess at. A fuzzy matcher would score a prettier F1 and be the wrong tool. | Stated |
| 18 | **The ZATCA chain sequencer is single-process, and that is a boundary, not an oversight.** `ChainStore` keeps `ctl.egs_chain_state` in memory with a `threading.Lock` per EGS device, so the eight-lane concurrency test is eight threads sharing one store. It cannot exercise the case that matters in a real deployment -- two worker **processes**, or a retried Fabric job, both reading `last_icv = n` and both minting `n+1`, which forks the chain into two documents claiming the same ICV. A submitted ICV cannot be withdrawn, so that fork is unrecoverable. `commit_signed` does guard it: it re-reads the head and refuses the write if it moved (compare-and-set, not read-then-write), and `test_chain_head_guard_refuses_a_stale_write_rather_than_forking` proves the refusal fires by advancing the head out of band -- the test was verified to fail when the guard is removed. **The durable half is now built** (2026-11-21). `src/mizan/spark/chain_head.py` runs the same compare-and-set over `ctl.egs_chain_state` as a Delta table, which Delta serialises through its transaction log, and `ChainStore` takes it as an injected `head_store` so the clearance engine stays free of Spark (ADR-008). The winner is decided by reading the head back and checking it carries **its own invoice hash**, not by asking Delta how many rows the UPDATE touched -- that count has to be read from the table history after the write, by which time another writer may have committed again, so it is not reliably the number you wrote. **The race test immediately found a defect in the implementation it was written for:** creating the chain-head table lazily inside the compare-and-set meant two writers starting the same chain both tried to CREATE it, and the loser got a `ProtocolChangedException` thrown at it instead of a clean `False` -- Delta's own error text says so ("multiple writers are writing to an empty directory... creating the table ahead of time will avoid this conflict"). The table is now created empty up front, and Delta's conflict exceptions are caught and answered by the read-back rather than propagated, because losing a race is a normal outcome here and not an error. Seven tests, including two racing writers on an existing chain and two racing to start a new one (the empty-table path is a MERGE, not an UPDATE, so it needs its own race). **Two things this still does not claim:** the races are driven by threads against a real transaction log rather than by two OS processes, because what is under test is whether the storage layer serialises conflicting head advances and Delta does that identically whoever asks; and it is **not wired in by default**, because `run_zatca` is single-process, where the in-memory head is accurate and a Delta round trip per signature would cost real time for no safety. It is the mechanism a multi-worker deployment needs, built and tested rather than promised. What remains genuinely unprotected is the head advance and the journal write together: a process dying between them leaves an ICV **gap**, which `verify_chain` detects from genesis and which is recoverable -- unlike a fork, which is neither. | Stated |
| 21 | **HTTP 409 is non-definitive by the frozen spec, and the retry is safe but cannot make progress.** Review asked whether retrying forever on 409 is wrong when the 409 means "already sent" -- i.e. the first attempt succeeded and its response was lost. Resending is safe: the retry carries the same `invoice_uuid` and the same signed bytes, so the portal cannot be made to hold a second document and no new ICV is minted. What it cannot do is resolve, so the pair can loop and an operator would see the attempt count climb. Resolving it needs a status query against the portal for that UUID, which the mock does not implement and which is **not built**. The definitive-status set is design-frozen (spec Section 12), so this is documented rather than quietly widened. | Stated |
| 23 | **The residency policy and the actual deployment region disagree, and the gate cannot see it.** `config/residency_policy.yml` declares `region: KSA` for every zone, and `residency_gate` (I-14) fails the pipeline when SECRET or TOP_SECRET data would land outside an approved region. The Fabric trial capacity this runs on is **UAE North**. The gate therefore passes against the *intended* in-Kingdom placement rather than the deployed one -- it validates the policy, not the hosting. Closing it is a capacity and workspace-region move to Azure Saudi Arabia (Dammam) plus a provisioning re-run; the policy file would not change, because it already says KSA. Raised by external review asking the question every regulated Saudi client asks first. | Open |
