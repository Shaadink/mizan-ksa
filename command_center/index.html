The engineering, not the animation

Four things an engineer would want to check before believing any number on this page.

1 · The key spine: why no row can be silently dropped

A reconciliation built as a LEFT JOIN from payments loses any bank line that has no matching payment — silently, forever. The spine is a UNION of keys from all three legs, so a row that exists anywhere survives into the result and shows up as a variance instead of vanishing.

spine AS (                       -- every key from ANY leg: nothing is dropped
    SELECT merchant_id, business_date_ksa FROM captures
    UNION SELECT merchant_id, business_date_ksa FROM settlements
    UNION SELECT merchant_id, business_date_ksa FROM gl
)

The settlement leg keys on settlement_for_date_ksa — the capture date a bank line pays for, not the date the file arrived. Keying on arrival would shift every line one day and balance to nothing.

2 · The circuit breaker: bad numbers do not get published

A singular dbt test fails the build when any merchant-day carries an unexplained variance. The system does not email you about bad numbers; it refuses to release them. Press B on this page to plant a one-halala defect and watch it fire.

-- assert_zero_unexplained_halala_variance.sql
SELECT * FROM {{ ref('fact_merchant_settlement_recon') }}
WHERE unexplained_bank_variance_sar <> 0.00
   OR unexplained_gl_variance_sar   <> 0.00

Detection is measured rather than assumed: 50 injected faults across six classes are caught at recall 1.000, and the one blind spot — offsetting errors on the same merchant-day — is asserted by a test so it cannot be quietly lost.

3 · Money is Decimal, and the boundary refuses floats

Not "we are careful with rounding" — the function raises rather than converting, so a float cannot enter by accident. A dbt test enforces the same rule in SQL.

def q2(value: Decimal) -> Decimal:
    if not isinstance(value, Decimal):
        raise TypeError(f"money must be Decimal, got {type(value).__name__}")
    return value.quantize(HALALA, rounding=ROUND_HALF_UP)

Validating against ZATCA's own SDK (3.0.8) found the same class of bug in the validator: BR-KSA-50 compares line VAT in IEEE-754 doubles, computing 96.00 × 0.15 = 14.399999999999999 and rejecting our exact 14.40.

4 · Lineage is a build gate, not a diagram

Every Gold column must trace to its source columns through OpenLineage, or the build raises. It currently stands at —, and it has caught every new Gold model since — including the newest one, twice.
